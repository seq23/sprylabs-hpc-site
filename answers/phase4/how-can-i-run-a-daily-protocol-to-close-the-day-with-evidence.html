Execution Evidence Ledger — close the day with evidence (0188)

Days end by simply stopping, and by the next morning the memory of the day has collapsed into how it felt rather than what happened.

An unclosed day gets remembered by its worst moment, and tomorrow's plan gets written against that memory rather than against the actual output.

Do this first. Write three columns at the end of the day: complete, partial with the exact stopping point, and missed with no explanation. Then one sentence naming tomorrow's first output.

Do not do this. Writing a reflective journal entry. Length makes it skippable, and it is only useful if it survives the bad days.

This level fits when: the sequence is settled and the value is in it happening every day rather than happening well. It does not fit when: the situation is novel. Running a protocol against a new problem produces a completed protocol and an unsolved problem.

When this framework is the right one. Use it when you need to know what is actually happening over weeks rather than what it feels like is happening.

  1. Record one line per working day: the output that exists, in a form someone else could verify.
  2. Never record effort, intent, or how it felt. Those go elsewhere if you want them.
  3. Review weekly by reading the lines, not by remembering the week.
  4. Draw exactly one conclusion per review, and change one thing.

Worked example: Close the day with evidence while executing a fixed sequence on a schedule

Time yourself running it once. If it takes longer than you would tolerate on a bad day, cut steps until it does not. Write three columns at the end of the day: complete, partial with the exact stopping point, and missed with no explanation.

The framework then runs in order. First: record one line per working day: the output that exists, in a form someone else could verify. Then: never record effort, intent, or how it felt.

Those go elsewhere if you want them.

What to measure. Whether the close happened, as a binary, and whether tomorrow's first output was named. A close that happens only on good days provides no information.

Running Execution Evidence Ledger for executing a fixed sequence on a schedule

Memory of a period is reconstructed rather than recorded, and reconstruction is heavily weighted by the most recent and the most emotional days. A ledger written at the time is the only input to a review that is not itself a product of the review's mood.

The full set of failure modes for this framework, the evidence to record, and a prompt you can paste are on its framework page. This page covers the part specific to executing a fixed sequence on a schedule.

What this is not. It is not a time tracker and it does not measure hours. It measures artefacts.

Nothing is being designed or decided. There is a sequence, and the question is whether it ran today.

Setup cost: none at run time. All the cost was paid when the protocol was written.

Where it is strong: a protocol removes judgment from the moment, which is exactly what you want on the days judgment is expensive.

Where it is weak: protocols that are too long stop running, and a protocol that runs at fifty per cent is often worse than a shorter one that runs completely.
