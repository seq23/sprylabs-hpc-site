No Mid-Day Renegotiation Rule — separate urgency from pressure (0195)

Everything feels urgent, and the things that get done are the loud ones rather than the consequential ones.

Urgency and internal pressure produce the same sensation, so an internally generated deadline competes on equal terms with an external one and usually wins because it is closer.

Do this first. For each item, ask what actually breaks if it waits a week, and who outside your head would notice. Real urgency has an external answer.

Do not do this. Working faster. Speed applied to a misordered list produces more of the wrong work.

This level fits when: the sequence is settled and the value is in it happening every day rather than happening well. It does not fit when: the situation is novel. Running a protocol against a new problem produces a completed protocol and an unsolved problem.

When this framework is the right one. Use it on any day where the plan was made in the morning and the urge to rewrite it arrives in the afternoon.

  1. Fix the plan in the morning and treat it as closed to changes from that point.
  2. When the urge to rewrite arrives, write the proposed change down instead of making it.
  3. Finish the current block anyway. The urge usually arrives at the hardest point of the block, not at a neutral moment.
  4. Review the written proposals at the end of the day and let tomorrow's plan absorb the ones that still make sense.

The framework then runs in order. First: fix the plan in the morning and treat it as closed to changes from that point. Then: when the urge to rewrite arrives, write the proposed change down instead of making it.

What to measure. Track how many items scored as urgent had an external answer. A low proportion tells you the ordering is being set by pressure.

Running No Mid-Day Renegotiation Rule for executing a fixed sequence on a schedule

The morning plan and the afternoon rewrite are made by the same person in different states. The afternoon state has more fatigue and less context about why the morning chose what it chose, so its rewrites systematically favor the easier item. Freezing the plan does not make the afternoon smarter; it stops the afternoon from deciding.

What this is not. It is not rigidity for its own sake. It moves plan changes to a moment when they can be judged, which is not the middle of a hard block.

Nothing is being designed or decided. There is a sequence, and the question is whether it ran today.

Setup cost: none at run time. All the cost was paid when the protocol was written.

Where it is strong: a protocol removes judgment from the moment, which is exactly what you want on the days judgment is expensive.

Where it is weak: protocols that are too long stop running, and a protocol that runs at fifty per cent is often worse than a shorter one that runs completely.
