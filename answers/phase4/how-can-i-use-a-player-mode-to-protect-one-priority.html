Arbitration Engine — protect one priority (0127)

Several projects are technically active, all of them get some attention, and none of them has produced a visible result in weeks.

Parallel projects share time in whatever proportion the day's noise dictates, which usually means no project gets a block long enough to reach a result.

Do this first. Name one project foreground for a period measured in weeks, give every other active project a written maintenance floor, and let the foreground take every contested block.

Do not do this. Trying to give each project a fair share. Fairness at the project level produces failure at every project.

This level fits when: you want the same standard applied across sessions and you are willing to re-seed it. It does not fit when: the task genuinely needs a different standard. Forcing one mode onto everything is how modes stop meaning anything.

When this framework is the right one. Use it when two or more things genuinely deserve the same block and the tie is not breaking on its own.

  1. Name the competing options explicitly, at most three. More than three is not arbitration, it is an unmade decision.
  2. Score each on leverage, urgency, energy fit, compounding, and downside if skipped.
  3. Say which dimension you are letting decide, before you look at the totals.
  4. Write the losing option's next review date so it is parked rather than abandoned.

Running Arbitration Engine for running the system's high-standard operating mode

Ties do not break by thinking harder, because the two options are close on the dimension you are thinking about. Scoring them on five named dimensions moves the comparison somewhere the difference is visible, and forces the trade to be stated rather than felt.

What this is not. It is not a prioritization framework for a whole backlog. It is a tie-breaker for a specific block, run in a few minutes.

You are invoking a named mode with a fixed standard rather than asking an open question. The mode decides what counts as an acceptable answer.

Setup cost: knowing the mode's rules well enough to notice when it has stopped following them.

Where it is strong: a named mode is checkable. You can tell when it has drifted, which you cannot with an unnamed style.

Where it is weak: modes drift silently as a thread lengthens, and drift is easy to miss because each step is small.
