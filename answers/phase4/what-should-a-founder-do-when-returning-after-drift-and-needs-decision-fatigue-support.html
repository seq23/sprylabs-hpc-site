System Drift Recovery Protocol — decision fatigue while returning after drift

The system stopped some time ago, the exact date is unclear, and returning feels like it requires an explanation.

What is actually scarce here: a starting point. Everything is equally stopped so there is no obvious first move.

Do this first. Restart one component today, chosen because the others depend on it, and leave everything else stopped for a week.

Do not do this. Do not analyze the drift before restarting. The analysis becomes the project and the system stays stopped.

How do I stop spending the day's judgment on choices that repeat? Convert recurring low-consequence choices into standing defaults with written override conditions.

When this framework is the right one. Use it when a system you were running has quietly stopped and you are considering a full rebuild.

  1. List the components of the system as it was, without judging them.
  2. Mark each one running, intermittent, or stopped, using evidence rather than memory.
  3. Restart exactly one stopped component, the one the others depend on most.
  4. Wait a week before restarting a second. Drift usually came from running more components than the week supports.
