Foreground Priority Selection Rule — choose the first task (0185)

The list is visible, the hours are available, and the first twenty minutes go to deciding rather than working. Often the item chosen is the one that was easiest to start.

Choosing at the start of a block means choosing at the moment you have the least context and the most inertia. The decision is being made in the worst possible conditions.

Do this first. Write the first output the night before, as one sentence, somewhere you will physically see it in the morning. Do not decide in the morning.

Do not do this. Ranking the whole list. Ranking is a much larger task than choosing one item, and it is frequently how the block gets spent.

This level fits when: the sequence is settled and the value is in it happening every day rather than happening well. It does not fit when: the situation is novel. Running a protocol against a new problem produces a completed protocol and an unsolved problem.

When this framework is the right one. Use it when several projects are all technically active and none of them is visibly moving.

  1. Name one project as foreground for a stated period, measured in weeks rather than days.
  2. Give every other active project an explicit background status with a maintenance floor: the minimum that keeps it from decaying.
  3. When a block is contested, the foreground project takes it. This is the entire rule and its whole value is that it is decided in advance.
  4. Review the foreground choice on a fixed date, not when a background project starts feeling urgent.

The framework then runs in order. First: name one project as foreground for a stated period, measured in weeks rather than days. Then: give every other active project an explicit background status with a maintenance floor: the minimum that keeps it from decaying.

What to measure. Record whether the first block went to the item named the night before. That single binary field, over two weeks, tells you whether the problem is the choosing or the list.

Running Foreground Priority Selection Rule for executing a fixed sequence on a schedule

Parallel projects do not share time evenly; they share it in whatever proportion the day's noise dictates, which usually means none of them gets a block long enough to produce a result. Naming one foreground project does not stop the others; it decides in advance which one wins a contested block.

The full set of failure modes for this framework, the evidence to record, and a prompt you can paste are on its framework page. This page covers the part specific to executing a fixed sequence on a schedule.

What this is not. It is not a ban on other work. Background projects continue at their maintenance floor; they just stop winning contested blocks.

Nothing is being designed or decided. There is a sequence, and the question is whether it ran today.

Setup cost: none at run time. All the cost was paid when the protocol was written.

Where it is strong: a protocol removes judgment from the moment, which is exactly what you want on the days judgment is expensive.

Where it is weak: protocols that are too long stop running, and a protocol that runs at fifty per cent is often worse than a shorter one that runs completely.
