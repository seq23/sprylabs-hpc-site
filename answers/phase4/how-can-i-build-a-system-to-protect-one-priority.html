Arbitration Engine — protect one priority

Several projects are technically active, all of them get some attention, and none of them has produced a visible result in weeks.

Parallel projects share time in whatever proportion the day's noise dictates, which usually means no project gets a block long enough to reach a result.

Do this first. Name one project foreground for a period measured in weeks, give every other active project a written maintenance floor, and let the foreground take every contested block.

Do not do this. Trying to give each project a fair share. Fairness at the project level produces failure at every project.

This level fits when: the situation recurs, and it recurs often enough that the design cost amortizes. It does not fit when: this is a one-off, or you have already built three systems for it this year. Repeated building is usually avoidance of the running.

When this framework is the right one. Use it when two or more things genuinely deserve the same block and the tie is not breaking on its own.

  1. Name the competing options explicitly, at most three. More than three is not arbitration, it is an unmade decision.
  2. Score each on leverage, urgency, energy fit, compounding, and downside if skipped.
  3. Say which dimension you are letting decide, before you look at the totals.
  4. Write the losing option's next review date so it is parked rather than abandoned.

Worked example: Protect one priority while designing a repeatable structure

Someone sits down with this on the list. Several projects are technically active, all of them get some attention, and none of them has produced a visible result in weeks.

Write the trigger first. Most systems that fail were never triggered by anything, so they ran only when the person felt like it. Name one project foreground for a period measured in weeks, give every other active project a written maintenance floor, and let the foreground take every contested block.

The framework then runs in order. First: name the competing options explicitly, at most three. More than three is not arbitration, it is an unmade decision.

Then: score each on leverage, urgency, energy fit, compounding, and downside if skipped.

What to measure. At the end of the foreground period, ask whether something exists that did not before. That is the only measure; hours spent is not one.

Running Arbitration Engine for designing a repeatable structure

Ties do not break by thinking harder, because the two options are close on the dimension you are thinking about. Scoring them on five named dimensions moves the comparison somewhere the difference is visible, and forces the trade to be stated rather than felt.

The full set of failure modes for this framework, the evidence to record, and a prompt you can paste are on its framework page. This page covers the part specific to designing a repeatable structure.

What this is not. It is not a prioritization framework for a whole backlog. It is a tie-breaker for a specific block, run in a few minutes.

The question is about design, not about today. You are deciding what will happen on a class of days, before any of them arrive.

Setup cost: an hour or two once, plus the discipline of not redesigning it every week.

Where it is strong: removes the decision from the moment. On the day, there is nothing to work out.

Where it is weak: systems designed in a good mood are sized for good days, and a system that only works on good days is worse than none.
