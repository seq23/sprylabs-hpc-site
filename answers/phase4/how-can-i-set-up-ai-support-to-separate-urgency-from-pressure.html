Foreground Priority Selection Rule — separate urgency from pressure

Everything feels urgent, and the things that get done are the loud ones rather than the consequential ones.

Urgency and internal pressure produce the same sensation, so an internally generated deadline competes on equal terms with an external one and usually wins because it is closer.

Do this first. For each item, ask what actually breaks if it waits a week, and who outside your head would notice. Real urgency has an external answer.

Do not do this. Working faster. Speed applied to a misordered list produces more of the wrong work.

This level fits when: the behavior you want is stable and you want it by default. It does not fit when: you are still working out what you want. Configuring an unsettled preference makes it harder to change.

When this framework is the right one. Use it when several projects are all technically active and none of them is visibly moving.

  1. Name one project as foreground for a stated period, measured in weeks rather than days.
  2. Give every other active project an explicit background status with a maintenance floor: the minimum that keeps it from decaying.
  3. When a block is contested, the foreground project takes it. This is the entire rule and its whole value is that it is decided in advance.
  4. Review the foreground choice on a fixed date, not when a background project starts feeling urgent.

The framework then runs in order. First: name one project as foreground for a stated period, measured in weeks rather than days. Then: give every other active project an explicit background status with a maintenance floor: the minimum that keeps it from decaying.

What to measure. Track how many items scored as urgent had an external answer. A low proportion tells you the ordering is being set by pressure.

Running Foreground Priority Selection Rule for configuring standing assistance

Parallel projects do not share time evenly; they share it in whatever proportion the day's noise dictates, which usually means none of them gets a block long enough to produce a result. Naming one foreground project does not stop the others; it decides in advance which one wins a contested block.

The full set of failure modes for this framework, the evidence to record, and a prompt you can paste are on its framework page. This page covers the part specific to configuring standing assistance.

What this is not. It is not a ban on other work. Background projects continue at their maintenance floor; they just stop winning contested blocks.

You are putting something in place that will be there tomorrow without being rebuilt: standing instructions, a stored template, a routine you can invoke by name.

Setup cost: a short configuration session, plus a cold test in a fresh context.

Where it is strong: it applies without you remembering to apply it, which is where most of the value is.

Where it is weak: configuration is invisible once set, so a bad rule keeps operating silently until you go and read it again.
