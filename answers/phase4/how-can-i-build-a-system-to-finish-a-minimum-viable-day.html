Recovery Mode Operating Rule — finish a minimum viable day

On low-capacity days the choice presents as the whole plan or nothing, and it usually resolves to nothing.

The normal plan was written for a different day, and negotiating with it consumes the capacity that was available.

Do this first. State the capacity before opening the list, name one output that would make today non-zero, write its finished state, and defer everything else in writing.

Do not do this. Doing a normal day at reduced quality. It produces a day that is neither finished nor rested, and no template for the next low day.

This level fits when: the situation recurs, and it recurs often enough that the design cost amortizes. It does not fit when: this is a one-off, or you have already built three systems for it this year. Repeated building is usually avoidance of the running.

When this framework is the right one. Use it in a stretch of days where capacity is genuinely reduced and is not going to bounce back tomorrow.

  1. Declare the mode explicitly and give it an end date or a review date. An undeclared reduction is just a decline.
  2. Set the reduced standard in writing: what a completed day looks like while the mode is on.
  3. Suspend anything that only works at full capacity, by name, rather than letting it fail quietly.
  4. Review on the date. Either exit the mode or extend it deliberately, and if you extend twice, get outside input.

Worked example: Finish a minimum viable day while designing a repeatable structure

Someone sits down with this on the list. On low-capacity days the choice presents as the whole plan or nothing, and it usually resolves to nothing.

Write the trigger first. Most systems that fail were never triggered by anything, so they ran only when the person felt like it. State the capacity before opening the list, name one output that would make today non-zero, write its finished state, and defer everything else in writing.

The framework then runs in order. First: declare the mode explicitly and give it an end date or a review date. An undeclared reduction is just a decline. Then: set the reduced standard in writing: what a completed day looks like while the mode is on.

What to measure. Whether the one output was completed and whether you stopped at the stop condition. Two binary fields.

Running Recovery Mode Operating Rule for designing a repeatable structure

Reduced capacity handled by pretending produces a run of failed normal days, and a run of failed days ends the system. Declaring reduced capacity as a mode, with its own smaller standard, keeps the system installed through the stretch so there is something to return to.

The full set of failure modes for this framework, the evidence to record, and a prompt you can paste are on its framework page. This page covers the part specific to designing a repeatable structure.

What this is not. It is not treatment, and it is not advice about burnout, illness, or mental health. If the reason for the reduced capacity is health, that belongs with a qualified professional and this rule only governs the work commitments around it.

The question is about design, not about today. You are deciding what will happen on a class of days, before any of them arrive.

Setup cost: an hour or two once, plus the discipline of not redesigning it every week.

Where it is strong: removes the decision from the moment. On the day, there is nothing to work out.

Where it is weak: systems designed in a good mood are sized for good days, and a system that only works on good days is worse than none.
