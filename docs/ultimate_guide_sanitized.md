# Master Operating Manual

## Client Intake → Auto Repo Generator Factory

### For near-$0 GEO / AEO / AI-discoverability content systems

Use this as the master document for building repeatable “velocity repos” that support a canonical business domain.

---

## 1. Purpose

This system exists to turn a business, site, or offer into a repeatable content and discoverability engine.

The output is not just a website. The output is a validated repo system that can:

* reinforce a canonical domain
* create highly extractable answer surfaces
* capture long-tail, comparison, emotional, and community phrasing
* support low-cost publishing velocity
* be deployed cheaply
* be updated safely
* be cloned across clients

This system is for:

* GEO
* AEO
* AI-answer discoverability surfaces
* AI answer visibility
* query capture around a core offer

This system is not a guarantee of traffic or citations. It is the structural layer that makes discovery, extractability, and answer visibility more possible.

---

## 2. Core model

Every build has two layers.

### Layer A — Canonical domain

This is the main business domain.

It should own:

* brand trust
* primary offer
* main CTA
* core conversions
* main authority identity

### Layer B — Velocity repo / supporting site

This is a separate repo, and often a separate domain or subdomain.

Its job is to:

* capture more question surfaces
* cover comparisons
* cover emotional phrasing
* cover common community phrasing
* publish answer pages cheaply
* reinforce canonical concepts
* link people and crawlers back toward canonical assets

The velocity repo is not the conversion center. It is the surface area engine.

---

## 3. Success standard

A “99/100” build means:

* titles are unique
* internal links are sound
* important pages are highly extractable
* page contracts are enforced
* terminology is normalized
* comparison surfaces exist
* answer surfaces exist
* hub structure exists
* velocity engine exists
* validators pass
* packaging is correct
* shipped artifact matches intended state

It does not mean:

* guaranteed rankings
* guaranteed citations
* guaranteed leads
* guaranteed crawl speed
* guaranteed revenue

## 4. Factory principles

### Principle 1 — Canonical first

The business site is the authority target.

### Principle 2 — Velocity repo supports canonical

The supporting site exists to widen retrieval and discovery opportunities.

### Principle 3 — Prewritten before automated

Do not automate until the language and structure are approved.

### Principle 4 — Validators are mandatory

If you cannot validate it, you cannot scale it.

### Principle 5 — Packaging must be validated

Never trust the working folder alone.

### Principle 6 — Distribution is separate

A strong repo without distribution is incomplete.

### Principle 7 — Clone process, not chaos

The value is in a factory system you can reuse.

### 8.1 BUSINESS_SOURCE_OF_TRUTH.md

# Business Source of Truth

## Business

* Name: business legal or operating name
* Canonical domain: primary domain that should hold authority
* Category: main industry or service category
* Geography: relevant city, state, region, or market footprint
* Business model: services, ecommerce, SaaS, media, marketplace, or mixed

## Main Offer

* Primary offer: the main product or service
* Secondary offers: supporting services, adjacent offers, or upsells
* Primary CTA: the main conversion action
* Main conversion page: page most responsible for action

## Audience

* Primary buyer: best-fit target customer
* Secondary buyer: adjacent or lower-priority buyer
* Core pain: main problem they need solved
* Core urgency: why action matters now
* Core objections: reasons they hesitate
* Emotional states: fear, confusion, urgency, overwhelm, skepticism, hope
* Preferred language: words and framing they naturally use

## Positioning

* Main differentiators: what sets the business apart
* Competitor set: direct alternatives
* Substitute set: indirect alternatives or “do nothing” alternatives
* Prohibited framing: language the brand should avoid
* Required framing: language the brand should reinforce
* Named methods/processes: proprietary methods, frameworks, or branded language

## Canonical Role

* What canonical domain must do: convert, explain, establish trust, hold primary authority
* Pages that should receive authority: top commercial or educational pages
* Pages that should receive traffic: pages intended to capture demand
* Pages that should convert: pages designed to generate contact, purchase, or signup

## Velocity Role

* Velocity brand/domain: companion site, editorial site, or branded support site
* Relationship to canonical: explicit, light, or mostly behind-the-scenes
* Core page families: main content structures to be built
* Primary linking path: how supporting pages route into the main site
* Publishing cadence: daily, weekly, or manual schedule

## Compliance

* Required disclaimers: legal, medical, financial, or industry-required language
* Restricted claims: promises, performance claims, regulated language
* Restricted phrases: phrases that create legal, trust, or policy risk
* Review requirements: what must be reviewed before publishing

* hype language that overpromises
* regulated or risky phrases
* jargon the audience does not naturally use

* short line that explains who this is for
* short line that clarifies the practical outcome
* short line that reflects the brand’s stance

## Offer Framing

* how the primary offer should be described
* how alternatives should be described
* how comparisons should be framed without exaggeration

## Tone Rules

* Directness: clear, plain, useful
* Emotional intensity: calibrated to audience reality, not manipulative
* Formality: professional but readable
* Commercial pressure: present, but not pushy or deceptive

### Recommended page types

* “what people keep asking about…”
* “why people struggle with…”
* “best way to…”
* “is X better than Y?”
* “how people compare…”
* “what to do when…”

### Required safeguards

* queue tracking
* slug dedupe
* publish manifest
* uniqueness validation
* stable template usage
* no fabricated quotations or invented user discussion

### High-quality content engine workflow

#### Step 1 — Data acquisition

Goal: Collect community-derived questions and thread titles through compliant methods.

Allowed methods:

* official platform APIs
* approved first-party exports
* compliant manual research

Example: A modular Python structure that uses the official Reddit API through PRAW to fetch top-voted thread titles from specific subreddits and store them in a structured JSON format for trend analysis.

Data acquisition rules:

* use official APIs only
* respect rate limits and platform terms
* collect only the fields required for analysis
* store normalized results in structured JSON
* do not scrape around platform restrictions
* do not generate fake source data to fill gaps

Suggested filter:

* prioritize questions or threads with 30+ upvotes or equivalent engagement so the system focuses on topics with demonstrated interest

#### Step 2 — Analysis & ideation

Goal: Group similar questions into topic clusters and identify recurring user needs.

Action:

* cluster similar questions
* identify repeated pain points
* separate informational, comparative, and commercial intent
* map clusters to page families

Example task: Identify the top recurring pain points in these discussions and suggest a comprehensive outline that addresses them.

Analysis rules:

* preserve source meaning
* do not invent consensus
* do not overstate demand
* distinguish between repeated mention and verified truth

#### Step 3 — Draft generation

Goal: Convert approved outlines into high-quality content using the defined brand voice.

Action:

* generate drafts from approved outlines
* prioritize factual accuracy
* use concrete explanation and examples
* avoid generic filler

Example task: Based on these community insights, draft a 1,000-word informative article. Prioritize fact-checking and include clear analogies so the piece does not read like generic AI output.

Drafting rules:

* no fabricated claims
* no invented quotes
* no fake testimonials
* no unsupported outcomes
* no deceptive “people are saying” framing unless directly supported and accurately attributed in source notes

### Automation model

This velocity layer is designed to reach approximately 95% automation without removing human judgment from the critical checkpoints.

### Absolute minimum human checkpoints

* Strategy lock
* Prewritten approval pack approval
* Periodic audit of sampled outputs and validator failures

Everything else should be systemized through templates, validators, queue controls, and publishing workflows.

## 35. Recovery procedures

### If a validator fails

1. stop
2. inspect exact failing file(s)
3. fix root cause
4. rerun full validator suite
5. manually inspect affected surfaces

### If live deploy is wrong

1. inspect deployed file paths
2. inspect root structure
3. confirm required files exist
4. roll back to previous commit if needed

### If package is wrong

1. delete broken ZIP
2. rebuild from true repo root
3. reopen ZIP
4. verify key files
5. revalidate if possible

### If content direction is off

1. stop automation
2. revise Language Registry
3. revise prewritten pack
4. re-approve
5. regenerate affected families only

### If policy/compliance issues are found

1. stop publishing
2. locate all affected pages
3. remove fabricated, deceptive, or unsupported content
4. rerun compliance validators
5. manually review before republishing
